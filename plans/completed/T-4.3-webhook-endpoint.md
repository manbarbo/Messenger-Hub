## Objective

Implement the webhook endpoint that receives incoming messages, validates them, handles idempotency, and pushes to the queue.

---

## Acceptance Criteria

- [x] `POST /webhooks/messages` accepts `message_id`, `from`, `text`, `timestamp`
- [x] Returns `202 Accepted` immediately (does not wait for LLM processing)
- [x] Duplicate `message_id` returns `200 OK` with `{ status: "duplicate", conversationId }`
- [x] Invalid request body returns `400` with validation errors
- [x] Message inserted into MongoDB before queue push
- [x] Conversation created or retrieved for the phone number
- [x] Job pushed to queue with all required data

---

## Implementation Steps

### 1. Webhook Schema (Zod)

Create `src/presentation/dto/webhook-message.schema.ts`:

- `WebhookMessageSchema` — `message_id`, `from`, `text`, `timestamp` (ISO-8601), optional `clinic_id`
- Project already uses Zod for tool schemas; class-validator is not a dependency (global ValidationPipe is T-5.2)

### 2. Webhook Controller

Create `src/presentation/controllers/webhook.controller.ts`:

- `POST /webhooks/messages` via `CommandBus` → `ProcessIncomingMessageCommand`
- Clinic resolution: body `clinic_id` → `DEFAULT_CLINIC_ID` env → 400 if neither
- `202 Accepted` + `{ status: 'accepted', conversationId }` for new messages
- `200 OK` + `{ status: 'duplicate', conversationId }` when `message_id` already exists
- `400` + `{ error: 'ValidationError', message }` for invalid bodies (Zod) or missing clinic
- Uses `@Res({ passthrough: true })` to set per-response status codes while returning a JSON body
- Persistence + queue push happen inside `ProcessIncomingMessageHandler` (message insert → conversation create/reuse → queue push) before the controller returns

### 3. Presentation Module + Wiring

- `src/presentation/presentation.module.ts` — imports `CqrsModule`, registers `WebhookController`
- `AppModule` imports `PresentationModule`
- `.env.example` gains `DEFAULT_CLINIC_ID`

---

## Implementation Notes

- Deviated from the plan sketch: validation uses **Zod** (existing stack pattern) instead of class-validator decorators; global class-validator pipe remains T-5.2.
- Webhook body accepts optional `clinic_id` (DESIGN.md sample omits clinic); `ProcessIncomingMessageCommand` requires `clinicId`, so `DEFAULT_CLINIC_ID` env covers single-clinic dev setups.
- Duplicate handling is not an error — command result `duplicate: true` maps to HTTP 200 per DESIGN.md error catalog.
- No LLM call in the webhook path — controller only enqueues; worker (T-4.2) does AI processing.
