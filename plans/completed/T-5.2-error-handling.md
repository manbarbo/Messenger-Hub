## Implementation Steps

### 1. Domain Exception Filter

Created `src/presentation/filters/domain-exception.filter.ts`:

- `@Catch()` catch-all `ExceptionFilter`
- **HttpException handling:** normalize `getResponse()` to `{ error, message }`
  - Custom object bodies keep their `error` key when it differs from `message`
  - Nest default bodies fall back to `exception.name` as `error`
  - `statusCode` is not echoed (already on the HTTP status line)
- **Known domain errors:** `instanceof` mapping to DESIGN.md / DECISIONS.md catalog
- **Unknown / infrastructure errors:** 500 + `{ error: 'InternalServerError', message: 'Internal server error' }`; raw error logged via Nest `Logger`

### 2. Registration

Registered via `APP_FILTER` in `PresentationModule` (`@nestjs/core` — Nest 11 moved `APP_FILTER` out of `@nestjs/common`):

- Filter lives in presentation layer with other HTTP concerns
- `main.ts` stays thin
- Worker (`worker-main.ts`) is HTTP-less and unaffected

### 3. Validation Strategy (deviation)

**class-validator ValidationPipe is NOT added.**

- All presentation DTOs already validate with Zod and throw `BadRequestException({ error: 'ValidationError', message })`
- class-validator is not a dependency; a ValidationPipe without class-validator DTOs is dead code
- Consistent `{ error, message }` format is guaranteed by controllers + the global filter
- Global class-validator pipe remains optional future work if decorator DTOs are introduced

---

## Implementation Notes

- `instanceof` mapping preferred over `constructor.name` strings (type-safe, minification-safe)
- `LLMIterationLimitError` is a known domain condition (cataloged at 500) — its message is safe to expose; unknown infra errors get the generic 500 body
- Controllers that catch `ConversationNotFoundError` and rethrow `NotFoundException` still work — filter normalizes their body; the global filter also covers any uncaught domain errors from future handlers
- Nest 11: `APP_FILTER` imports from `@nestjs/core`, not `@nestjs/common`
