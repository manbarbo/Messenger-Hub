## Objective

Implement the `QueueService` adapter using BullMQ for development. Abstract queue behind domain interface for future SQS swap.

---

## Acceptance Criteria

- [x] `BullMQQueueService` implementing `QueueService` interface
- [x] `push()` method adds job to `message-processing` queue
- [x] Job payload includes `conversationId`, `messageId`, `from`, `text`, `clinicId`
- [x] Queue configured with retry logic (3 attempts, exponential backoff)
- [x] Dead Letter Queue for permanently failed jobs
- [x] `QueueModule` providing `QueueService` via DI

---

## Implementation Steps

### 1. BullMQ Queue Service

Create `src/infrastructure/queue/bullmq-queue.service.ts`:

- `BullMQQueueService implements QueueService, OnModuleDestroy`
- Main queue `message-processing` with `defaultJobOptions`: `attempts: 3`, `backoff: { type: 'exponential', delay: 1000 }`, `removeOnComplete: 100`, `removeOnFail: 500`
- DLQ queue `message-processing-dlq`; `pushToDlq(job)` moves permanently failed payloads (used by worker in T-4.2)
- Connection from `REDIS_HOST` / `REDIS_PORT` via `ConfigService` (defaults `localhost:6379`; empty env values fall back safely)
- `push()` adds job named `process-message` with the full `QueueJob` payload
- Closes both queues on `onModuleDestroy`
- Domain `QueueService` interface stays focused (`push` only) — DLQ method is adapter-level

### 2. Queue Module

Create `src/infrastructure/queue/queue.module.ts`:

- `@Global()` module (matches `EmbeddingModule` / `DatabaseModule` pattern) so application handlers can inject `QUEUE_SERVICE` without importing infrastructure modules
- Provides `{ provide: QUEUE_SERVICE, useClass: BullMQQueueService }`
- Exports `QUEUE_SERVICE`
- Imported by `AppModule`

### 3. DI rewiring

- Removed `QUEUE_SERVICE` provider/export from `InfrastructureModule` (was `InMemoryQueueService`)
- `AppModule` imports `QueueModule`
- `InMemoryQueueService` kept as a test/dev implementation of the same domain interface
- `infrastructure.module.spec.ts` updated: EventPublisher binding still asserted there; queue binding covered by `queue.module.spec.ts`; mock `QUEUE_SERVICE` added to mock deps so `ApplicationModule` handlers still resolve

---

## Implementation Notes

- Deviated from the plan sketch by marking `QueueModule` `@Global` — required because `ProcessIncomingMessageHandler` injects `QUEUE_SERVICE` via the domain token and `ApplicationModule` does not import infrastructure modules for cross-cutting services.
- `pushToDlq` is not on the domain `QueueService` interface (Interface Segregation); the worker infrastructure (T-4.2) will use the concrete adapter.
- `bullmq` was already a dependency; Redis was already in `docker-compose.yml` and `.env.example`.
