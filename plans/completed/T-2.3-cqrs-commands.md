## Objective

Implement CQRS command handlers for state mutations: `CreateAppointmentCommand`, `CancelAppointmentCommand`, `ProcessIncomingMessageCommand`.

---

## Acceptance Criteria

- [x] `CreateAppointmentCommand` + handler: validates slot availability, creates appointment in transaction, publishes `AppointmentCreatedEvent`
- [x] `CancelAppointmentCommand` + handler: validates appointment exists and is CONFIRMED, marks slot as available, publishes `AppointmentCancelledEvent`
- [x] `ProcessIncomingMessageCommand` + handler: inserts message, finds/creates conversation, pushes to queue
- [x] Handlers use repository interfaces (not infrastructure implementations)
- [x] Handlers publish domain events via `EventPublisher` interface
- [x] `CqrsModule` registered in application module

## Implementation Steps

### 1. Create Appointment Command

Create `src/application/commands/create-appointment/`:
- `create-appointment.command.ts` — Command class with `clinicId`, `doctorId`, `slotId`, `patientPhone`, `patientName?`
- `create-appointment.handler.ts`:
  1. Validate slot exists and `isBooked = false`
  2. Validate clinic and doctor exist
  3. Create appointment in transaction (appointment INSERT + slot UPDATE)
  4. Publish `AppointmentCreatedEvent`
  5. Return appointment

### 2. Cancel Appointment Command

Create `src/application/commands/cancel-appointment/`:
- `cancel-appointment.command.ts`
- `cancel-appointment.handler.ts`:
  1. Find appointment by ID
  2. Validate status is CONFIRMED
  3. Update status to CANCELLED
  4. Mark slot as available
  5. Publish `AppointmentCancelledEvent`

### 3. Process Incoming Message Command

Create `src/application/commands/process-incoming-message/`:
- `process-incoming-message.command.ts` — `messageId`, `from`, `text`, `timestamp`, `clinicId`
- `process-incoming-message.handler.ts`:
  1. Check if `message_id` already exists (idempotency)
  2. Find or create conversation for phone number
  3. Insert user message into MongoDB
  4. Push job to queue for LLM processing
  5. Return conversation ID

### 4. Event Handlers

Create `src/application/event-handlers/`:
- `appointment-created.handler.ts` — Log event (expandable for notifications)
- `appointment-cancelled.handler.ts` — Log event

## Implementation Notes

- Handlers live in `application/` and depend only on domain repository/service interfaces via DI tokens (`@nestjs/cqrs` `@CommandHandler`).
- **CreateAppointment** pre-validates: slot exists, `clinicId`/`doctorId` match the slot (FK-backed clinic/doctor existence), slot not booked, start time in the future (`PastDateError`). Transactional insert + slot book remains in `PrismaAppointmentRepository.create()`.
- **CancelAppointment** uses domain helper `cancelAppointment()` for the CONFIRMED → CANCELLED transition, then `appointmentRepository.update` + `slotRepository.markAsAvailable`. Throws new domain error `AppointmentNotFoundError` when missing.
- **ProcessIncomingMessage** is idempotent: existing `messageId` returns `{ conversationId, duplicate: true }` without re-insert or queue push. New messages create/find conversation (non-escalated), insert inbound user message, and `QUEUE_SERVICE.push` a `QueueJob`.
- **EventPublisher** interface implemented by `EventEmitterEventPublisher` (`EventEmitter2.emit(eventName, event)`). Bound in `InfrastructureModule`.
- **Event handlers** use `@OnEvent('appointment.created'|'appointment.cancelled')` and log (expandable later for notifications).
- **ApplicationModule** imports `CqrsModule` and registers command + event handlers.
- **InMemoryQueueService** bound as `QUEUE_SERVICE` until T-4.1 replaces it with BullMQ (same interface, swap provider only).
- AppModule wiring of `ApplicationModule`/`InfrastructureModule` remains deferred until `EMBEDDING_SERVICE` exists (T-3.2), so the app stays bootable.
- Added domain error `AppointmentNotFoundError` (explicit errors per AGENTS.md §19).
