## Objective

Define Zod schemas for all tool arguments and implement a validation layer that checks LLM-proposed tool calls before execution. Validation errors are returned to the LLM as tool results.

---

## Acceptance Criteria

- [x] Zod schema for `buscar_conocimiento`: `pregunta` (string, non-empty)
- [x] Zod schema for `consultar_disponibilidad`: `especialidad` (string), `sede` (string), `fecha` (YYYY-MM-DD regex)
- [x] Zod schema for `agendar_cita`: all consultar_disponibilidad fields + `hora` (HH:mm), `paciente_telefono` (string), `paciente_nombre?` (string)
- [x] Zod schema for `escalar_a_humano`: `motivo` (string, non-empty)
- [x] Domain validation layer: date not in past, clinic/specialty exists, slot available
- [x] Validation errors formatted as tool result strings for LLM feedback
- [x] `ToolValidator` service that combines Zod + domain validation
- [x] Tool definitions in OpenAI function-calling format

## Implementation Steps

### 1. Tool Schemas (Zod)

Create `src/application/llm/tool-schemas.ts`:
- Structural validation for all four tools
- `fecha`: `YYYY-MM-DD` + real calendar-date refine
- `hora`: `HH:mm` (00–23 / 00–59)
- `paciente_telefono`: length + phone character pattern
- Exported `TOOL_SCHEMAS` map and inferred arg types

### 2. Tool Definitions (OpenAI Format)

Create `src/application/llm/tool-definitions.ts`:
- Four tools as domain `LLMToolDefinition[]`
- JSON Schema `parameters` with `required` arrays matching schemas
- `additionalProperties: false`

### 3. Colombia Time Helpers

Create `src/application/llm/colombia-time.ts`:
- `America/Bogota` is fixed UTC-5 (no DST)
- Past-date checks compare Colombia calendar days / date-times
- Used by domain validation for `fecha` / `hora`

### 4. Domain Extensions for Validation

- `ClinicRepository.findByName(name)` — resolve `sede` → clinic (tenant-scoped)
- New `DoctorRepository.existsByClinicAndSpecialty(clinicId, specialty)`
- Prisma adapters + `InfrastructureModule` binding for `DOCTOR_REPOSITORY`

### 5. Tool Validator Service

Create `src/application/llm/tool-validator.ts`:
- `validate(toolName, args, { clinicId, now? })` → `{ valid, parsed | error }`
- Zod first; domain rules second
- Domain rules:
  - Past date/date-time in Colombia
  - Sede exists and belongs to `clinicId`
  - Specialty has an active doctor at the clinic
  - For `agendar_cita`: matching available slot for `fecha`+`hora`
- Errors are human-readable strings for LLM tool-result feedback
- Successful booking validation enriches `parsed` with `clinicId`, `slotId`, `doctorId`, `startUtc`
- `ApplicationModule` provides/exports `ToolValidator`

---

## Implementation Notes

- Domain validation is async (repository lookups); the orchestrator (T-3.4) awaits `validate` before executing tools.
- Specialty validation uses active doctors (not a hard-coded enum) so clinics can define their own specialties.
- Slot match compares exact Colombia `fecha`+`hora` against `slot.startTime` (UTC), consistent with seed times (`08:00` Colombia → `13:00Z`).
- Tenant check prevents LLM from booking against another clinic's sede name.
- Execution-time re-checks (slot race) remain the orchestrator/command responsibility (T-3.4 / appointment commands).
